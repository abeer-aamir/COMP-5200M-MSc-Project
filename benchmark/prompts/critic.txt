SHARED DEFINITIONS

Use exactly the same definitions as the specification generator.

- Public requirement: one entry in the requirements array.
- Resource-kind count: distinct required Kubernetes kinds excluding the task's mandatory Namespace.
  Every task must contain exactly one public Namespace requirement; Namespace counts toward the
  public-requirement total but not the resource-kind total. Namespace is the only permitted
  cluster-scoped task object.
- Dependency edge: a necessary directed relationship where `from` is the prerequisite requirement
  and `to` is the requirement whose satisfaction or meaningful verification depends on it. Mere
  co-location, repeated values, or unrelated resources do not qualify.
- Runtime behaviour: a distinct behaviour verifiable only through live state change over time or
  after an induced event. Point-in-time state does not qualify.
- Safety constraint: one public requirement whose central purpose is one measurable property from
  exactly one category: `pod_hardening`, `rbac_least_privilege`, `network_policy`,
  `resource_enforcement`.
- Interacting mechanism: one of configuration/secret projection; Service discovery/routing;
  startup/readiness/probe gating; batch scheduling/retry; RBAC; NetworkPolicy; persistent storage;
  disruption/availability; resource governance, with a real edge or runtime interaction connecting
  mechanisms.

AUDIT METHOD

Perform a complete independent audit. Do not trust the generator's counts, fingerprint labels,
hardness rationale, or blueprint claims. Recompute them from the actual requirements and graph.
Check every requirement and every blueprint; do not stop at the first defect.

1. CONTRACT AND STRUCTURE
- Recount requirements, distinct resource kinds, dependency edges, runtime behaviours, safety
  constraints, mechanism families, and relevant graph depth.
- Apply <difficulty_contract> exactly, including minima, maxima, and exact counts.
- Confirm every dependency edge references existing IDs, uses prerequisite -> dependent direction,
  and represents a real necessary dependency.
- Confirm runtime_behaviours and safety_constraints enumerate every and only the distinct public
  behaviours/constraints they claim; no double-counting or hidden packing.

2. ENVIRONMENT FEASIBILITY
The task must work on Kubernetes 1.35 in a fresh single-node Kind cluster with:
- a NetworkPolicy-enforcing CNI;
- cluster DNS and normal ClusterIP Service routing;
- the repository's tested namespaced PVC workflow;
- no internet;
- only `busybox:1.36.1` guaranteed for workloads;
- exactly one required task Namespace permitted as the only cluster-scoped task object;
- all other task resources namespaced and built-in;
- no CRDs/third-party controllers, cluster-scoped RBAC, PersistentVolume/StorageClass requirements,
  host mounts, hostNetwork, privileged containers, node mutation, cloud/external services, or host access.

Reject environment assumptions that rely on bash, Python, curl, GNU-specific behaviour, an
unavailable image/controller, timing races, unspecified Kubernetes semantics, arbitrary fixed
delays as correctness, or unbounded polling.

NetworkPolicy requirements are valid only for L4 behaviour the CNI can deterministically enforce.
Kubernetes documents that NetworkPolicy enforcement depends on the network plugin, so do not infer
enforcement from the API object alone; this frozen environment explicitly supplies an enforcing CNI.

3. PUBLIC/PRIVATE TRACEABILITY
- Every public bullet must correspond to exactly one private requirement, in the same order.
- Every private requirement must appear in exactly one public bullet.
- Every material name, kind, namespace, value, selector, port/protocol, path, permission, bound,
  dependency, runtime condition, and lifecycle condition must be preserved exactly.
- public_task_text must contain no requirement IDs, difficulty metadata, dependency metadata,
  blueprints, assertions, hardness rationale, likely failure modes, diversity information, previous
  task data, critic feedback, or other private material.
- The scenario paragraph may contain narrative color only. Flag any independent testable constraint,
  contradiction, or inconsistent duplicate.

4. BLUEPRINT FAIRNESS AND TESTABILITY
- There must be exactly one blueprint per requirement and no orphan blueprint.
- Each blueprint must test only public wording for that requirement.
- Equivalent implementations allowed by public wording must pass.
- No candidate-failure signal may introduce an unstated exact representation, extra-resource ban,
  stricter timeout, preferred implementation, or other hidden requirement.
- Runtime tests must identify the induced event where applicable, observe the required before/after
  behaviour, and respect the public bound.
- Every wait, setup, and success path must be bounded.
- Candidate-caused schema/admission/reference/runtime failures may reject the candidate.
  API/transport/evaluator failures that prevent a trustworthy observation must be classified for
  rerun, not candidate rejection.

5. INTERNAL CONSISTENCY AND ANTI-BYPASS
- No requirement may be impossible, contradictory, materially ambiguous, or dependent on
  unavailable infrastructure.
- Cross-resource names, keys, selectors, ports, paths, permissions, and dependency conditions must
  be mutually consistent.
- The intended central interaction must not be trivially bypassable while still satisfying the
  literal public wording.
- Difficulty must come from actual interactions, not descriptive length or repeated standalone
  resources.

6. DIVERSITY
Recompute the candidate's canonical resource-kind set and dependency topology from the actual
requirements/edges. Compare against every accepted fingerprint.
A material diversity defect exists if BOTH resource_kind_set AND dependency_topology_class match
one accepted task. Identify that task by its supplied task_id.
Runtime/safety overlap alone is not a rejection, but may support a minimum revision toward a
less-used mechanism if another material revision is already required.

HARDNESS ASSESSMENT

After correctness, independently classify structural hardness:
- `matches_contract`: actual structure satisfies the supplied difficulty contract and interaction
  depth is consistent with it;
- `easier_than_contract`: actual structure falls below the contract or uses nominal resources/edges
  without the required interaction depth;
- `harder_than_contract`: actual structure exceeds a contract maximum/exact count or adds deeper
  interaction than the selected tier permits.

For `very_hard`, also require a real dependency path of at least three edges, a genuine fan-in or
fan-out point, at least two workload-controller roles, at least two bounded reversible induced
changes, and at least one recovery that depends on multiple Kubernetes mechanisms converging.
Nominal counts without this interaction structure are `easier_than_contract`.

Give one concise sentence citing the concrete counts/edges/mechanisms that determine the result.
Any hardness mismatch must also appear as a `contract_violation` finding, because an accepted task
must match its selected contract.

DECISION

- `accept`: zero material findings.
- `revise`: one or more material defects are present and each can be repaired without replacing the
  task's core mechanism.
- `reject`: the core scenario/mechanism is infeasible, contradictory, or invalid such that no local
  revision can produce a fair task without redesigning it.

Do not reject merely because several local fixes are needed. Do not accept with findings.
A revise/reject verdict must contain at least one finding.

FINDINGS

Report every distinct material defect, deduplicating downstream symptoms with one cause.
Do not report style preferences, harmless brevity, optional implementation choices, or unsupported
speculation.

For each finding provide:
- requirement_id: the affected ID when applicable; use an empty string only when no single
  requirement applies;
- defect_type: exactly one of
  `contract_violation`, `ambiguity`, `infeasible`, `non_deterministic_check`,
  `unjustified_hidden_check`, `leakage`, `insufficient_diversity`, `environment_violation`,
  `traceability_gap`, `core_redesign_required`;
- defect_location: exactly one of `private_specification`, `verification_blueprint`,
  `public_task_text`;
- evidence: concrete text/field/count/edge demonstrating the defect;
- minimum_revision_instruction: the smallest sufficient fix plus dependent consistency changes.
  Leave this empty only for a `core_redesign_required` finding under `reject`.

When one root cause affects multiple requirements, cite all affected IDs in the evidence but do not
duplicate the same finding.
