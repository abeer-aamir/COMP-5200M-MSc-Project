SHARED DEFINITIONS

Apply these definitions exactly. The critic uses the same definitions.

- Public requirement: one entry in the requirements array. Requirements are counted by entries,
  not by clauses hidden inside prose.
- Resource-kind count: the number of distinct Kubernetes kinds required by the task, excluding
  the task's mandatory Namespace object. Every task must contain exactly one public Namespace
  requirement; Namespace counts toward the public-requirement total but not the resource-kind total.
  Namespace is the only permitted cluster-scoped task object.
- Dependency edge: a necessary directed relationship between two public requirements.
  `from` is the prerequisite requirement and `to` is the requirement whose satisfaction or
  meaningful verification depends on that prerequisite. Mere co-location in a namespace,
  repeated values, or unrelated resources do not count.
  Examples that can qualify when genuinely necessary: ConfigMap/Secret -> workload that consumes
  it; workload labels -> Service that selects it; Service/dependency -> initContainer or readiness
  gate that waits for it; ServiceAccount/Role -> RoleBinding; workload labels -> NetworkPolicy or
  PodDisruptionBudget that selects it.
- Runtime behaviour: a distinct behaviour that can be verified only by observing live cluster
  state changing over time or after an induced event. A single point-in-time manifest/API read
  does not count. Every distinct runtime behaviour must appear exactly once in runtime_behaviours
  and must be explicitly required by public wording.
- Safety constraint: one explicit public requirement whose central purpose is one measurable
  safety property from exactly one of these categories:
  `pod_hardening`, `rbac_least_privilege`, `network_policy`, `resource_enforcement`.
  Do not count one requirement as multiple safety constraints by packing several unrelated safety
  categories into it.
- Interacting mechanism: one of these mechanism families participating in a real cross-requirement
  interaction: configuration/secret projection; Service discovery/routing; startup/readiness/probe
  gating; batch scheduling/retry; RBAC; NetworkPolicy; persistent storage; disruption/availability;
  resource governance. Two mechanisms interact only when at least one real dependency edge or one
  runtime behaviour requires them to work together.

ENVIRONMENT CONTRACT

Design only tasks that are executable in this frozen environment:

- Kubernetes 1.35 on a fresh single-node Kind cluster.
- A NetworkPolicy-enforcing CNI is installed.
- Cluster DNS and normal ClusterIP Service routing are available.
- The environment supports the repository's tested namespaced PVC workflow; do not require a
  cluster-scoped PersistentVolume or StorageClass object.
- Workloads have no internet access.
- `busybox:1.36.1` is the only guaranteed workload image. Never require any other image.
- Every task must require exactly one core/v1 Namespace for its own namespace. Every other required
  object must be a namespaced, built-in Kubernetes 1.35 resource and must explicitly use that
  namespace.
- No CRDs, third-party controllers, cluster-scoped RBAC, hostPath/other host mounts, hostNetwork,
  privileged containers, node mutation, external services, cloud load balancers, or host access.
- BusyBox commands must be compatible with the locked BusyBox image. Do not require bash, Python,
  curl, GNU-specific utilities/flags, or any tool not guaranteed by the frozen brief/environment.
- All startup, recovery, and runtime checks must be bounded. A condition-based bounded poll is
  acceptable when it tests the real dependency; an arbitrary fixed delay or an unbounded loop is not.
- Do not rely on timing races, unspecified Kubernetes behaviour, implementation-specific scheduler
  choices, or defaults that materially affect correctness.
- Do not design a ResourceQuota/LimitRange or PodDisruptionBudget interaction that prevents the
  evaluator's bounded probe objects or cleanup/recovery from being admitted on a single-node cluster.

TASK-DESIGN RULES

Difficulty must come from interacting constraints, dependency depth, runtime behaviour, and safety,
not from trivia, obscure API details, repeated resources, gratuitous prose, or hidden assumptions.

Before writing the task, mentally construct at least one feasible solution in this environment.
If you cannot explain how every requirement could be satisfied together, redesign the task.

Write one short scenario paragraph containing narrative context only. It must not introduce an
independent testable constraint. Put every testable obligation in exactly one requirement.
The requirements must include exactly one explicit Namespace requirement.

Write requirements R01, R02, ... in stable order. Each requirement must be:
- direct, atomic, and independently traceable;
- measurable with deterministic Kubernetes state or a bounded live test;
- explicit about every material name, namespace, kind, image, label/selector, count, key, path,
  port/protocol, command condition, permission, numeric value/bound, dependency, and lifecycle
  condition needed for fair evaluation;
- phrased so a solver has implementation freedom only where that freedom is genuinely acceptable.

Do not smuggle multiple unrelated obligations into one requirement merely to stay within a count.
Naturally inseparable subclauses may remain together only when they define one observable property.

All runtime requirements must state the externally visible behaviour and its public time bound.
Do not make a hidden test's timeout stricter than public wording.

Do not create fake dependency edges to satisfy the difficulty contract. Every edge must change what
must exist or be true before the dependent requirement can be meaningfully satisfied or verified.
The central interaction of the task must not be bypassable by a candidate that technically satisfies
the words while avoiding the intended dependency.

DIFFICULTY CONTRACT

Obey the supplied <difficulty_contract> exactly. Recompute the following from the actual task before
responding rather than trusting your own summaries:
- public requirement count;
- distinct resource-kind count excluding Namespace;
- dependency-edge count and graph depth;
- number of distinct runtime behaviours;
- number of safety constraints;
- number of interacting mechanism families.

If the selected contract contains a minimum, meet or exceed it without gratuitous filler. If it
contains an exact value or maximum, obey it exactly.

DEPENDENCY GRAPH

List every and only real dependency edge using existing requirement IDs.
Use the direction `from = prerequisite`, `to = dependent`.
The textual reason must identify the concrete selector/reference/consumption/gating relationship.
The graph should normally be acyclic; do not create circular startup dependencies.

VERIFICATION BLUEPRINTS

Produce exactly one private verification blueprint per public requirement, and no extras.
Each blueprint must contain:
- requirement_id;
- observable_state;
- bounded setup/precondition, if any;
- one deterministic assertion or a clearly ordered set of assertions that together test only that
  requirement;
- timeout_seconds;
- candidate_failure_signals;
- infrastructure_failure_signals.

Blueprint rules:
- Every candidate-failure assertion must be justified by explicit public wording. No hidden
  requirement, stricter timeout, preferred implementation, extra resource ban, or unstated default.
- Equivalent Kubernetes implementations must pass whenever the public requirement permits them.
- For runtime behaviour, specify the induced event (if any), the before/after observable, and the
  public bound. Restore evaluator-created changes where applicable.
- Candidate-caused admission/schema/reference/runtime failures are candidate failures.
  API unavailability, command-channel/transport failure, evaluator setup failure, or other evidence
  that prevents a trustworthy observation is infrastructure and must request rerun rather than
  candidate rejection.
- Every success path and wait must be bounded.

DIVERSITY

diversity_fingerprints is a private campaign-control ledger. Never expose it publicly.

Hard diversity rule:
- The new task must not match any accepted task on BOTH canonical resource_kind_set AND
  dependency_topology_class.

Soft diversity rule:
- Prefer runtime-behaviour types and safety categories used less often in the ledger.
- Changing only names, ports, labels, or scenario wording is not meaningful diversity.

The diversity fingerprint is descriptive, not a loophole: derive it after finalizing the task.
Do not rename a topology class merely to evade a match. resource_kind_set must be the sorted,
deduplicated set of required kinds excluding Namespace. Use the project's canonical topology
labels from the supplied ledger/brief; if no canonical label applies, use one stable structural
description and ensure the critic can reproduce it from dependency_edges.

REVISION HANDLING

On the first round, previous_specification is empty.
On a revision round, start from previous_specification. Fix every material item in revision_feedback
and every dependent field required for consistency. Preserve unaffected requirement IDs, exact
values, wording, graph edges, and blueprint content. Do not redesign unrelated parts.

If a required fix would violate the difficulty contract, make the minimum additional change needed
to restore the contract and record that dependent change in the affected private rationale fields.
Never satisfy feedback by merely relabelling a fingerprint or hiding a requirement.

1. Recount all contract quantities from the actual requirements and graph.
2. Verify every edge uses existing IDs, the required direction, and a real dependency.
3. Verify every distinct runtime behaviour and safety constraint appears exactly once in its

8. Compare the canonical resource-kind/topology pair against every supplied accepted fingerprint.
9. Verify no private authoring material appears in public requirement text.
