An internal operations portal needs configuration updates to appear without a rollout while the service remains available during routine pod replacement.

- Create a Namespace named `medium-portal-ns`.
- In namespace `medium-portal-ns`, create a ConfigMap named `portal-content` containing exactly one key, `index.html`, with value `portal-version=v1` followed by a newline.
- In namespace `medium-portal-ns`, create an Opaque Secret named `portal-token` containing exactly one key, `API_TOKEN`, with value `medium-token`.
- In namespace `medium-portal-ns`, create a Deployment named `portal-web` with exactly two replicas and pod label `app=portal-web`. Its single container must be named `web`, use `busybox:1.36.1`, set `API_TOKEN` from `portal-token/API_TOKEN` using `secretKeyRef`, mount the complete `portal-content` ConfigMap read-only at `/www`, and run `sh -c "test \"$API_TOKEN\" = medium-token && httpd -f -p 8080 -h /www"`. Expose named TCP container port `http` on 8080 and use an HTTP readiness probe with path `/` on named port `http`, `periodSeconds: 5`, and `failureThreshold: 3`. Both pods must become Ready within 60 seconds. If an evaluator changes `portal-content/index.html` to `portal-version=v2\n`, every Ready `portal-web` pod must serve exactly that new body within 120 seconds without a Deployment rollout; after the evaluator restores the original value, every Ready pod must serve `portal-version=v1\n` again within 120 seconds.
- Harden every `portal-web` pod with pod-level `runAsNonRoot: true`, `runAsUser: 1000`, `runAsGroup: 1000`, and `fsGroup: 1000`, and container-level `allowPrivilegeEscalation: false`, `readOnlyRootFilesystem: true`, and `capabilities.drop: ["ALL"]`.
- In namespace `medium-portal-ns`, create a ClusterIP Service named `portal-svc` selecting `app=portal-web`, with TCP port 80 targeting named port `http`. With both replicas Ready, an in-namespace client labelled `access=portal` must receive exactly `portal-version=v1` followed by a newline from `http://portal-svc`. If an evaluator deletes one `portal-web` pod, ten requests made through `portal-svc` at one-second intervals after the deleted pod is absent from the Ready endpoint set must all succeed, and a replacement pod with a different UID must become Ready within 60 seconds.
- In namespace `medium-portal-ns`, create a NetworkPolicy named `portal-ingress` selecting `app=portal-web`. It must allow ingress on TCP 8080 only from pods in the same namespace labelled `access=portal`, with all other ingress to the selected pods denied.
- In namespace `medium-portal-ns`, create a PodDisruptionBudget named `portal-pdb` selecting `app=portal-web` with `minAvailable: 1`.
- Configure Deployment `portal-web` with `RollingUpdate` strategy, `maxUnavailable: 0`, `maxSurge: 1`, `minReadySeconds: 5`, `progressDeadlineSeconds: 90`, and `revisionHistoryLimit: 2`.
- Set Secret `portal-token` to `immutable: true`.
