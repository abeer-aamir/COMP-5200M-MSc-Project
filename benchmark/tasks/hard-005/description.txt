Could you put together a small node-monitoring setup in a namespace called `hard-monitor-ns`? It is only for our one-node Kubernetes 1.35 Kind environment, with no workload internet, and `busybox:1.36.1` is the image available for every container.

The node agent should serve a tiny health file from a ConfigMap named `agent-content`. That ConfigMap contains exactly one key, `health`, with `agent-ready` and a newline. Run the agent as DaemonSet `node-agent`, labelled `app=node-agent` and `role=agent`, so there is exactly one Ready agent pod on the single schedulable node within 60 seconds. Its only container is also called `agent`; mount the complete ConfigMap read-only at `/www`, run `httpd -f -p 8082 -h /www`, expose named TCP port `agent-http` on 8082, and use an HTTP readiness probe on `/health` every five seconds. Use RollingUpdate with `maxUnavailable: 1`. Expose it through ClusterIP Service `agent-svc`, port 8082 targeting `agent-http`.

The collector has a separate ConfigMap called `collector-content`, containing only `index.html=collector-ready\n` and `health=ok\n`, plus an immutable Opaque Secret named `monitor-token` with only `MONITOR_TOKEN=monitor-secret`. Create Deployment `monitor-collector` with two replicas and labels `app=monitor-collector` and `role=collector`. It needs exactly one init container called `wait-agent` which checks `http://agent-svc:8082/health` every two seconds until the exact body is `agent-ready`, failing after 30 attempts instead of waiting forever.

The main collector container is named `collector`. Load `MONITOR_TOKEN` from the Secret with a Secret key reference, mount the complete collector ConfigMap read-only at `/www`, expose named TCP port `collector-http` on 8080, and run `sh -c "test \"$MONITOR_TOKEN\" = monitor-secret && httpd -f -p 8080 -h /www"`. Its readiness probe should be an exec check which requires the local `/health` body to equal `ok` and the agent Service `/health` body to equal `agent-ready`; run it every five seconds with failure threshold three. Also use HTTP startup and liveness probes for local `/health`, allowing 60 seconds for startup and checking liveness every ten seconds. Both collector replicas should be Ready within 90 seconds. Configure RollingUpdate with `maxUnavailable: 0`, `maxSurge: 1`, `minReadySeconds: 5`, and `progressDeadlineSeconds: 120`.

Run every agent, collector, init, and checker container as non-root UID/GID 1000 with `fsGroup: 1000`, no privilege escalation, a read-only root filesystem, and all capabilities dropped. None of these workloads needs the Kubernetes API, so disable automatic service-account token mounting on their pod templates.

Put ClusterIP Service `collector-svc` in front of the collector, using port 80 and named target `collector-http`. An in-namespace pod labelled `access=monitor` should get exactly `collector-ready\n` from it. If one Ready collector pod is deleted and has left the Ready endpoint set, ten one-second Service requests should all succeed, and a different-UID replacement should be Ready within 60 seconds. Add a PodDisruptionBudget called `collector-pdb` selecting `role=collector` with `minAvailable: 1`.

Use exactly four NetworkPolicies. `monitor-default-deny` should select pods whose role is `agent` or `collector` and deny both ingress and egress. `agent-ingress` should allow TCP 8082 to agent pods only from collector pods. `collector-ingress` should allow TCP 8080 to collector pods only from pods labelled either `access=monitor` or `role=monitor-checker`. `collector-egress` should let collector pods reach agent pods on TCP 8082 and cluster DNS on UDP and TCP port 53, with no other collector egress. An unlabelled test pod should not reach either Service.

Set container defaults with LimitRange `monitor-defaults`: requests of 20m CPU and 32Mi memory and limits of 200m CPU and 128Mi memory. ResourceQuota `monitor-quota` should have exact hard limits of eight pods, three Services, two batch Jobs, two CronJobs, one CPU and 512Mi memory in requests, and two CPUs and 1Gi memory in limits. Leave enough room for the normal three application pods, a collector surge, an agent replacement, one checker Job, and one temporary evaluator pod.

Create a suspended CronJob called `monitor-check`, scheduled every five minutes with `Forbid` concurrency and one successful and one failed Job retained. Its pod label is `role=monitor-checker`; its single hardened `checker` container should make up to 30 attempts, sleeping two seconds between failures, to get exactly `collector-ready` from `http://collector-svc`, then print `monitor-check-ok`. Use `restartPolicy: Never` and an active deadline of 90 seconds. A Job created from it should Complete within 90 seconds and log exactly `monitor-check-ok` followed by a newline.

There is also one failure-and-recovery case I care about. If an evaluator temporarily patches `node-agent` with an impossible node selector so that it has no Ready agent pod, both collectors should become NotReady and `collector-svc` should have no Ready endpoints within 45 seconds. Once the original DaemonSet template is restored, an agent with a different UID and both collectors should be Ready within 90 seconds, and the collector Service should return to two Ready endpoint addresses.
