We need a small authenticated note endpoint in `medium-auth-ns`. Its content is simple, but a pod should only be considered Ready while its own service account can read the one Secret it is meant to use. Losing that permission must withdraw both replicas from the Service rather than leave apparently healthy endpoints behind.

Create immutable Opaque Secret `auth-content` with only `DATA=auth-ready`. The application identity is ServiceAccount `auth-reader`, with token automount explicitly enabled. Give it Role `auth-content-reader`, granting exactly `get` on the core `secrets` resource with `resourceNames: [auth-content]` and nothing else, then bind only that ServiceAccount to the Role using `auth-content-reader-binding`.

Deployment `auth-web` has two `app=auth-web` replicas and uses `auth-reader`. Its one `busybox:1.36.1` container projects the Secret's `DATA` key as `/content/index.html` and has an `emptyDir` at `/work`. Every three seconds it should make a bearer-token HTTPS GET to the Kubernetes API for only `auth-content` in its own namespace, with each request bounded to five seconds. Create `/work/authorized` only when that request succeeds and the returned `DATA` decodes to `auth-ready`; remove the marker otherwise. Serve `/content` on named TCP port `auth-http` at 8080. An exec readiness probe every five seconds, with failure threshold two, must require both the authorization marker and the exact local response. Use RollingUpdate with no unavailable replicas, one surge, five ready seconds and a 150-second progress deadline. Both replicas need to be Ready within 150 seconds.

Expose them using ClusterIP Service `auth-svc`, port 80 to `auth-http`; its response must be exactly `auth-ready` with no extra bytes. Add `auth-pdb` selecting `app=auth-web`, with `minAvailable: 1` and no `maxUnavailable`.

Run the application as non-root UID/GID 1000 with `fsGroup: 1000`, no privilege escalation, a read-only root filesystem and all capabilities dropped. `/work` is its only writable path.

The authorization transition is part of the task. If `auth-content-reader-binding` is saved and deleted, both pods must become NotReady and `auth-svc` must lose all Ready endpoints within 60 seconds. Restoring that exact binding must recover two endpoints and the exact body within 120 seconds, and the restoration should be attempted even if an earlier assertion fails. Once authorization has recovered, deleting one Ready application pod must produce a different-UID Ready replacement within 60 seconds while the remaining replica keeps the exact Service response available.
