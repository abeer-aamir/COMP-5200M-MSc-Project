We need a small internal release portal that does not come up until its durable release marker is in place, and I would like the user-facing endpoint kept separate from the backend that owns the content. Put the whole thing in `very-hard-release-ns` on our Kubernetes 1.35 Kind environment. Workloads cannot get to the internet, so use the available `busybox:1.36.1` image throughout.

Start with a mutable ConfigMap called `release-page` whose only entry is `index.html` containing `release=v1` followed by a newline. The backend also needs an immutable Opaque Secret, `release-token`, containing only `TOKEN=release-key`. Give the namespace a `release-state` claim requesting exactly 64Mi with `ReadWriteOnce`. A Job called `release-seed` should mount it at `/state` and, without overwriting an existing marker, write `schema-1\n` to `/state/schema`. Its single `seed` container should then verify that value and print `release-seed-ok`. Use `restartPolicy: Never`, no backoff and a 90-second active deadline; it should finish inside that time and its log should contain only the success line.

The backend is a two-replica Deployment named `release-backend`, with pod labels `app=release-backend` and `role=backend`. Before each backend starts, a `wait-seed` init container should mount the state claim read-only and check every two seconds for the exact `schema-1` marker, failing after 45 unsuccessful checks instead of waiting forever. The only main container is `backend`. Feed its `TOKEN` from the Secret using a key reference, mount the complete page ConfigMap read-only at `/srv` and the state claim read-only at `/state`, and have it verify both the token and marker before running httpd on 8080 with `/srv` as its root. Name that TCP port `backend-http`, check `/` for readiness every five seconds with a failure threshold of three, disable automatic service-account token mounting, and have both replicas Ready within 120 seconds. `release-backend-svc` should be a normal ClusterIP Service on TCP 8080 targeting that named port; a pod carrying `role=gateway` must receive exactly `release=v1\n` from it.

Put a second two-replica Deployment, `release-gateway`, in front, labelled `app=release-gateway` and `role=gateway`. Its `wait-backend` init container should give the backend Service at most 60 attempts, two seconds apart, to return the exact v1 body. The main `gateway` container needs a writable emptyDir at `/www`; every two seconds it should copy a successful backend response to `/www/index.html`, remove that file when a fetch fails so readiness is withdrawn, and serve the directory with httpd on named TCP port `gateway-http` at 8081. An HTTP readiness probe on `/` should run every five seconds with failure threshold two. Disable its API token and use RollingUpdate with `maxUnavailable: 0`, `maxSurge: 1`, `minReadySeconds: 5`, `progressDeadlineSeconds: 150` and `revisionHistoryLimit: 2`; both gateways should be Ready within 150 seconds.

Expose those gateways as `release-svc`, port 80 to `gateway-http`. A client labelled `access=release` should get exactly `release=v1\n`. Once both replicas are Ready, deleting one and waiting until it is absent from the Ready endpoints must not interrupt twelve requests made a second apart, and a replacement with a different UID should be Ready within 75 seconds. Add `release-backend-pdb` and `release-gateway-pdb`, each selecting the matching `app` label and using `minAvailable: 1` with no `maxUnavailable`.

Please isolate this with exactly five NetworkPolicies. `release-default-deny` selects the backend and gateway roles and denies ingress. `backend-from-gateway` admits TCP 8080 to backend pods only from gateway pods. `gateway-from-clients` admits TCP 8081 to gateway pods only from `access=release` clients or `role=release-audit` pods. `seed-isolation` selects `job-name=release-seed` and denies ingress, while `audit-isolation` does the same for `role=release-audit`. An unlabelled client should not be able to use either Service.

All init and application containers in the two Deployments, as well as the seed and audit containers, should run as non-root UID and GID 1000 with `fsGroup: 1000`, no privilege escalation, a read-only root filesystem and all Linux capabilities dropped. Only give them writable emptyDir or PVC mounts where their commands actually need to write. Reserve a `release-auditor` ServiceAccount for the checks, with a Role named `release-page-reader` containing exactly one rule: `get` on the core ConfigMap named `release-page`. `release-page-reader-binding` should bind only that ServiceAccount to that Role.

The audit itself is a suspended CronJob called `release-audit`, scheduled for `*/15 * * * *`, using `Forbid` concurrency and retaining one successful and one failed Job. Its pod is labelled `role=release-audit`, uses the auditor ServiceAccount, and has one `audit` container that gives `release-svc` up to 60 two-second attempts to return the exact v1 body before printing `release-audit-ok`. Use `restartPolicy: Never` and a 150-second active deadline. If one Job is created from this template while v1 is active, it should Complete within 150 seconds and its sole pod should log exactly that one line.

Add container defaults with `release-defaults`: requests of 20m CPU and 32Mi memory, and limits of 200m CPU and 128Mi memory. `release-quota` should set `pods: "12"`, `persistentvolumeclaims: "2"`, `requests.storage: "256Mi"`, `services: "4"`, `count/jobs.batch: "4"`, `count/cronjobs.batch: "2"`, `requests.cpu: "2"`, `requests.memory: "1Gi"`, `limits.cpu: "4"` and `limits.memory: "2Gi"`. Leave enough of that allowance for the steady workloads, a gateway surge, an audit Job and evaluator probes.

Finally, content changes need to travel through the real chain rather than forcing a rollout. If `release-page/index.html` is changed to `release=v2\n`, both Ready backend pods and both Ready gateway pods should serve those exact bytes within 150 seconds without either Deployment generation or any of the four pod UIDs changing. Restoring the ConfigMap to v1 should restore all four responses within another 150 seconds, again without a rollout.
