Please build a small status page in `medium-status-ns`. It should deliberately withdraw itself from the Service when its projected mode says to hold traffic, then recover in place when the mode returns to normal.

Use a mutable ConfigMap named `status-mode` with only `MODE=ready`. Deployment `status-web` has two replicas labelled `app=status-web`, each running one `busybox:1.36.1` container. Mount the ConfigMap at `/mode` and an `emptyDir` at `/www`. Every two seconds write `status=ready\n` to `/www/index.html` only while the projected mode is `ready`; remove the output for any other value. Serve `/www` on named TCP port `status-http` at 8080 and probe `/` every five seconds with failure threshold two. Disable service-account token mounting. Use RollingUpdate with zero unavailable and one surge, five ready seconds, a 120-second progress deadline and revision history limit two. Both replicas should be Ready within 120 seconds.

ClusterIP Service `status-svc` exposes port 80 to `status-http` and selects `app=status-web`. A pod labelled `access=status` must receive exactly `status=ready\n`. Default-deny ingress to the application and permit TCP 8080 only from that client label; an unlabelled client must not connect.

Run the status container as non-root UID/GID 1000 with `fsGroup: 1000`, no privilege escalation, a read-only root filesystem and all capabilities dropped. `/www` is the only writable path. Add `status-pdb` for `app=status-web` with `minAvailable: 1` and no `maxUnavailable`. LimitRange `status-defaults` should provide container requests of 20m CPU/32Mi memory and limits of 200m CPU/128Mi memory.

There are two recovery behaviours to preserve. Changing `MODE` to `hold` must make both pods NotReady and remove all Ready endpoints from `status-svc` within 60 seconds, without changing the Deployment generation or pod UIDs. Restoring `ready` must recover two endpoints and the exact response within 120 seconds, again without rollout. After recovery, delete one Ready pod once it has left the endpoint set; ten requests made one second apart through the Service must all return the exact body, and a different-UID replacement must be Ready within 60 seconds.
