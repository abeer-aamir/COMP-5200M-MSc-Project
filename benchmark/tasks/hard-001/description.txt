Could you set up a small internal report service for us in Kubernetes? I want it kept in a namespace called `hard-report-ns`, including all the application resources, and this is for our local Kubernetes 1.35 Kind setup. There is no workload internet access, so please stick to the `busybox:1.36.1` image we already have.

The page content should come from a ConfigMap called `report-content`. For now that ConfigMap should only have `index.html`, containing `report-version=v1` with the usual newline at the end. There is also an Opaque Secret called `report-token`; its only entry is `ACCESS_TOKEN=hard-report-token`, and I want that Secret marked immutable.

The actual web workload is a Deployment called `report-web`. It needs two replicas, the pods should use `app=report-web`, and there should only be one container in each pod, named `web`. Have it load `ACCESS_TOKEN` from the Secret with a `secretKeyRef`, mount the complete report ConfigMap read-only at `/www`, expose an `http` TCP port on 8080, and run `sh -c "test \"$ACCESS_TOKEN\" = hard-report-token && httpd -f -p 8080 -h /www"`. The readiness check should be HTTP `/` on that named port every five seconds with a failure threshold of three, and both replicas should be Ready within 60 seconds. Please use pod security settings `runAsNonRoot: true`, `runAsUser: 1000`, `runAsGroup: 1000`, and `fsGroup: 1000`; for the web container I also need privilege escalation disabled, a read-only root filesystem, and all Linux capabilities dropped. It does not need Kubernetes API access, so switch off automatic service-account token mounting on these pods.

Put a normal ClusterIP Service named `report-svc` in front of it, port 80 to the named `http` target. A pod in the namespace with `access=report` should get exactly `report-version=v1` and a newline from `http://report-svc`. Please keep this available during an ordinary single-pod replacement: once both replicas are Ready, if one is deleted and has left the Ready endpoint set, ten calls through the Service at one-second intervals should all work, and a replacement with a different UID should be Ready within 60 seconds.

Ingress should be closed down with a NetworkPolicy called `report-ingress`. It should select the report pods and only allow TCP 8080 from same-namespace pods carrying `access=report`; other ingress to those pods should be denied. Add `report-pdb` with `minAvailable: 1` as well. The Deployment itself should use RollingUpdate with `maxUnavailable: 0`, `maxSurge: 1`, `minReadySeconds: 5`, `progressDeadlineSeconds: 90`, and `revisionHistoryLimit: 2`.

We also reserve an identity for report checks. Create ServiceAccount `report-runner`, a Role called `report-content-reader`, and RoleBinding `report-content-reader-binding`. The Role should contain exactly one rule: core API group, ConfigMaps, resource name `report-content`, verb `get`. Bind only that ServiceAccount to it; it should not gain list, watch, Secret access, write access, or access to a different ConfigMap.

There should be one Job named `report-smoke` using that ServiceAccount. Label its pod `access=report`, use one `busybox:1.36.1` container named `smoke`, and run `sh -c "i=0; until body=$(wget -qO- http://report-svc 2>/dev/null); do i=$((i + 1)); [ \"$i\" -ge 30 ] && exit 1; sleep 2; done; test \"$body\" = report-version=v1 && echo report-smoke-ok"`. It should use `restartPolicy: Never`, `backoffLimit: 0`, and `activeDeadlineSeconds: 60`. In a normal run it needs to complete inside 60 seconds and its only pod should log just `report-smoke-ok` followed by a newline.

One last thing is important for how we update reports. If `report-content/index.html` is changed to `report-version=v2\n`, both Ready web pods should start serving that exact body within 120 seconds without the Deployment generation or pod UIDs changing. Once the ConfigMap is put back to v1, both should serve the original value again within another 120 seconds, still without a rollout.
